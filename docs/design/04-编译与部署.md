## 1. 工具链要求

| 工具 | 版本 | 用途 |
|---|---|---|
| Rust | **1.95.0**（MSRV；gpui-pre 传递要求——T-G00 Spike#9 评审升级；gpui-kit 0.7.1 / gpui-pre 0.3.8 已在 1.95.0 上实测可编） | 全部 crate；MSRV 变更视为破坏性变更，需 RFC |

`rust-toolchain.toml`（仓库根目录，提交入库）：

```toml

components = ["rustfmt", "clippy"]
profile = "minimal"
```

**MSRV 政策**：落后 stable 两个次版本以内；CI 含 `cargo +1.85 check` 通道（仅编译检查，不跑测试）防止漂移。

## 3. 构建命令与 feature 矩阵

### 3.1 常规构建

```bash
git clone https://github.com/flyl3una/hzip.git
cd hzip

# 开发构建（含全部格式 + GUI）
cargo build                       # 全 workspace
cargo build -p hzip-cli           # 仅 CLI
cargo build -p hzip-gui           # 仅 GUI

# 测试
cargo test --workspace            # 单元 + 集成
cargo test -p hzip-fmt-zip --test conformance    # 单格式一致性套件
cargo nextest run --workspace     # 推荐：更快、支持重试隔离

# 质量门禁（等价于 PR CI）
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo deny check licenses advisories
python build/checks/deps-direction.py    # 依赖方向检查（架构 §3.1）
```

### 3.2 feature 矩阵

| 目标 | 命令 | 说明 |
|---|---|---|
| 默认（全功能） | `cargo build --release` | 含 rar（unrar 许可允许解压用途分发） |
| 发行版合规构建 | `cargo build --release --no-default-features -p hzip-cli --features default-formats` | 剔除 rar，用于不能接受 unrar 许可的仓库 |
| 最小体积 | `cargo build --release -p hzip-cli --no-default-features --features default-formats` + `strip` | 见 §4.2 |
| GUI / CLI 独立 | `-p hzip-gui` / `-p hzip-cli` | 二者不互相依赖 |

workspace 根 `Cargo.toml` 片段：

```toml
[workspace.dependencies]
hzip-core   = { path = "crates/hzip-core", version = "0.1.0" }

sevenz-rust = { version = "0.6", features = ["compress", "aes256"] }
unrar       = { version = "0.5" }
tar         = "0.4"
flate2      = "1"
xz2         = "0.1"
zstd        = "0.13"
bzip2       = "0.4"
clap        = { version = "4", features = ["derive"] }
gpui-kit    = "=0.7.1"  # GUI 层（06 §1.2；0.7.1 内部把 gpui 指向 gpui-pre =0.3.8）
rust-embed  = "8"       # T-G50：自有 lucide 图标内嵌（assets/，构建离线；脚本入库一次性）
rfd         = "0.15"    # T-G52：原生文件选择对话框 + 扩展名过滤（UI 原生对话框收口例外——02 §5 平台红线不适用于 GUI 进程内对话框）
smol        = "2"       # GUI 信号回投通道（SignalTx/SignalRx，T-G00 contracts）
# ……版本唯一来源，各 crate 以 workspace = true 引用
```

## 4. 发布构建

### 4.1 Release profile

```toml
[profile.release]
lto = "thin"            # full LTO 收益 <2%，链接时间不可接受
codegen-units = 1
panic = "unwind"        # 不可用 abort：core 的 catch_unwind panic 隔离依赖 unwind
strip = "debuginfo"
opt-level = 3

[profile.release.package."*"]
opt-level = 3
```

### 4.2 二进制体积控制

| 手段 | 预期 |
|---|---|
| `strip = "debuginfo"` | 自动 |
| 剔除未用格式 feature | 每格式约缩减 5–15% |
| `cargo bloat` 纳入 CI 报告（不阻塞） | 监控膨胀 |
| 目标：CLI ≤ 8 MB、GUI ≤ 15 MB（不含平台运行时） | 超标在发布评审说明 |

### 4.3 交叉编译

| host → target | 工具 | 备注 |
|---|---|---|
| x86_64-linux → aarch64-linux | `cross-rs`（Docker） | CI 专用 |
| mac(intel) ↔ mac(arm) | rustup 双 target + `lipo` | 产 universal binary |
| win → 任意 | 不支持交叉（unrar/msvc 限制） | Windows 目标只在 Windows runner 构建 |

```bash
# Linux arm64 示例
cargo install cross
cross build --release --target aarch64-unknown-linux-gnu -p hzip-cli
```

## 5. 平台打包与分发

统一由 [`build/package/package.py`](../../build/package/README.md) 驱动：**一条命令产出一个
平台的全部安装包**，本地与 CI 跑的是同一条命令（打包只做打包，构建二进制交给 `cargo`/CI）。

```bash
python build/package/package.py --target <triple> --formats msi,zip        # Windows
python build/package/package.py --target x86_64-apple-darwin,aarch64-apple-darwin --formats dmg
python build/package/package.py --target <triple> --formats tar.gz,deb,rpm,appimage
python build/package/package.py --target <triple> --dry-run               # 只看计划（含缺什么工具）
```

产物与 `sha256sums.txt` 落 `dist/`（CI 用 `dist-installers/`）；版本号唯一来源是根
`Cargo.toml` 的 `[workspace.package].version`，发版用 `--check-tag vX.Y.Z` 断言一致。

> **历史与取舍**：曾计划用 **cargo-dist** 产 portable 归档与 shell/powershell 安装器
> （`dist-workspace.toml`），但该链路从未跑通——仓库 pin 的 0.28 读不了那份配置
> （要求 `[workspace]`/`[package]` 根表、`cargo-dist-version` 必须三段式 semver），
> 且 0.28 的可执行文件叫 `dist`（`cargo dist` 不存在）、没有 `publish` 子命令，
> `ci = ["github"]` 还要求 github.com 的 `repository`（当时主仓在 Gitee，2026-10-12 已迁至 GitHub）。
> 现由 `build/package` 自持归档与安装包，发布走 `softprops/action-gh-release`。
> 若要恢复 shell 一键安装器：按上述三条修好配置后接 `dist build --artifacts=global`。

### 5.1 Windows

| 产物 | 内容 |
|---|---|
| `hzip-<ver>-x86_64-pc-windows-msvc.zip` | 两个 exe + README.txt + LICENSE*（有则带），免安装 |
| `hzip-<ver>-setup-x86_64.msi`（WiX v5） | 安装向导（`WixUI_InstallDir`，可选目录）→ Program Files；开始菜单 + 桌面快捷方式；系统 PATH；App Paths；ProgID `hzip.Archive` + 「打开方式」登记；含卸载 |
| `hzip-<ver>-setup-arm64.msi` | 同上（`wix build -arch arm64`；arm64 二进制由同一 runner 交叉，04 §4.3） |

**MSI 干什么、不干什么**（与 §8 验收项对应）：

* **干**：装文件/快捷方式/PATH/App Paths；登记 ProgID + `OpenWithProgids`（只进「打开方式」，
  **不改** .zip/.7z 的默认程序）；**系统注册**——`HKLM\SOFTWARE\RegisteredApplications` 里写
  `hzip → SOFTWARE\hzip\Capabilities`，并在 `Capabilities\FileAssociations` 逐扩展名指向
  `hzip.Archive`，于是 hzip 出现在「设置 → 应用 → 默认应用」的候选里，用户可自行设为 .zip 等格式的
  默认程序（**登记**而非篡夺默认值）。命令行侧：`hzip.exe` 进系统 PATH 且 `App Paths` 登记，
  新开的 cmd/PowerShell 直接 `hzip --version` 可用；GUI 侧：开始菜单/桌面快捷方式与 ARP 条目
  一律显示为 `hzip`（可执行文件名 `hzip-gui.exe` 不出现在用户可见处）。
  大版本升级 `MajorUpgrade`（同版本可重装、低版本拒绝），升级保留用户配置
  （配置在 `%APPDATA%\hzip`，MSI 从不触碰）。
* **不干**：右键菜单的注册/注销归**应用运行时**（04 §5.1 下方 HKCU 段）——verb 挂到
  `*`/`Directory` 会改写其 Shell 默认值，卸载要「精确还原原值」，只有写过它的应用知道原值。
  MSI 只落 `hzip-shell.dll` / `hzip-shellmenu.msix` 两个文件（可选 feature，缺载荷就不含）。
* 用户数据默认保留；`msiexec /x <msi> REMOVEUSERDATA=1` 才连 `%APPDATA%\hzip` 与
  `%LOCALAPPDATA%\hzip` 一起清（§8 的卸载残留检查用这个开关）。
* 卸载只回收 MSI 自己写的东西（组件 GUID 固定不变，见 `build/package/templates/windows/hzip.wxs.in` 头注）；
  其中 `SOFTWARE\hzip`、`SOFTWARE\Classes\hzip.Archive`、两处 `App Paths\*.exe` 是**整个键属于我们**，
  用 `RemoveRegistryKey Action="removeOnUninstall"` 连子键一起删（避免空键残留）。

```powershell
# 本机（需 WiX v5：dotnet tool install --global wix --version 5.0.2）
cargo build --release --target x86_64-pc-windows-msvc -p hzip-cli -p hzip-gui
python build/package/package.py --target x86_64-pc-windows-msvc --formats msi,zip
```

系统集成注册（T-CM；由 `build/shell-ext/build-shell-ext.ps1` 产出，设置页「应用」写入）：

| 产物 | 用途 | 注册方式 |
|---|---|---|
| `hzip-shell.dll` | `IExplorerCommand` 实现 | 与 `hzip-gui.exe` 同目录；经典路径经 `HKCU\...\CLSID\{A7C4D1E8-…}\InProcServer32` 载入 |
| `hzip-shellmenu.msix` | 稀疏包（Windows 11 / Server 2025 现代菜单顶层入口） | `Add-AppxPackage -ExternalLocation "<安装目录>"` |

**Win11 顶层菜单的硬前提是包签名**：`Identity/@Publisher` 必须与签名证书 Subject
完全一致，且证书链被目标机信任（AppX 部署服务以 SYSTEM 运行，只认
`LocalMachine` 证书存储）。无有效签名时 `install` 自动回落经典注册（仅出现在右键
「显示更多选项」），并由设置页明示 `Degraded`。

本机开发/验收可直接用 `shell/cert/` 下的开发证书链（生成 → 管理员导入 →
打包签名 → 注册，四步见该目录 README）；发布则用受信任 CA 签发的证书。

```reg
; 文件关联（免管理员）
HKCU\Software\Classes\.zip\OpenWithProgids  →  hzip.Archive
; 经典右键路径（Win10 / Server 2016-2022 / Win11 兜底）：
;   HKCU\...\Classes\*\shell\hzip\ExplorerCommandHandler = {A7C4D1E8-…}
;   HKCU\...\Classes\Directory\shell\hzip\… 与 Directory\Background\shell\hzip\…
; 注意：在 `*` / `Directory` 上挂 verb 会把其 Shell 默认值置 "none"（防篡夺默认动词），
;       卸载时精确还原原值。
```

签名：MSI 与 DLL 使用代码签名证书（EV 优先）signtool 双签（SHA-256 + 时间戳）；无证书时发布 unsigned 并在 Release Notes 声明。

### 5.2 Linux

| 产物 | 说明 |
|---|---|
| `hzip-<ver>-<triple>.tar.gz` | 通用二进制，解压即用 |
| `hzip_<ver>_amd64.deb` / `_arm64.deb` | `/usr/bin/{hzip,hzip-gui}`、`.desktop`、AppStream 元数据、hicolor 图标、`/usr/share/doc/hzip`（GPL-3.0 全文，驱动自动装，§9） |
| `hzip-<ver>-<arch>.AppImage` | GUI 入口（`AppRun` → `hzip-gui`），内嵌 `.desktop`/图标/AppStream |
| `hzip-<ver>-1.<arch>.rpm` | rpmbuild spec（文件与 deb 等价；`AutoReqProv: no` + 显式 `Requires`，见下） |

```bash
# 本机（Debian/Ubuntu：apt install dpkg-dev rpm appstream desktop-file-utils）
cargo build --release --target x86_64-unknown-linux-gnu -p hzip-cli -p hzip-gui
python3 build/package/package.py --target x86_64-unknown-linux-gnu --formats tar.gz,deb,rpm,appimage
```

* `.desktop` / AppStream 元数据**先校验再进包**（`desktop-file-validate`、`appstreamcli validate`，
  缺工具只告警，`--no-validate` 显式跳过）；`.desktop` 名、AppStream `<id>`、图标名统一为
  `metadata.toml` 的 `app_id`（GNOME 按 app-id 找图标）。
* **中文字体是弱依赖**（不是从 `ldd` 推出来的，而是产品语义）：deb `Recommends: fonts-noto-cjk`、
  rpm `Recommends: google-noto-sans-cjk-fonts`（`metadata.toml` 的 `[deb]/[rpm] recommends`）——
  apt/dnf 默认会装，中文用户开箱即得；确实没有中文字体的机器上 GUI 会把界面回退英文（02 §12.2），
  不会变成整屏豆腐块。tar.gz/AppImage 没有包管理器可用，靠这条降级 + 文档。
* AppImage 工具（appimagetool + 交叉架构的 type-2 runtime）**按版本 + sha256 双锁**自动下载，
  缓存 `~/.cache/hzip-package`；跨架构产物用 `--runtime-file` 换 runtime，不会产出「宿主架构 runtime
  + 目标架构二进制」的坏包。
* deb/rpm 的依赖清单静态写在 `build/package/metadata.toml`（可从产物 `ldd` 反查，见该目录 README）。
* Nautilus 脚本仍**待 M4**：仓库还没有该脚本，驱动不会伪造；补上后加进 `stage_fhs` 即可。

`.desktop` 文件注册 MimeType：`application/zip;application/x-7z-compressed;application/x-rar-compressed;application/x-tar;application/gzip;application/x-xz;application/zstd;`。

### 5.3 macOS

```bash
# 一条命令出 universal .app + dmg（驱动内做 lipo / iconutil / codesign / notarytool）
cargo build --release --target x86_64-apple-darwin -p hzip-cli -p hzip-gui
cargo build --release --target aarch64-apple-darwin -p hzip-cli -p hzip-gui
python3 build/package/package.py \
  --target x86_64-apple-darwin,aarch64-apple-darwin --formats dmg,tar.gz

# 等价的手工步骤（驱动内部就是这些）
lipo -create hzip-x86_64 hzip-aarch64 -output hzip
lipo -archs hzip        # 驱动内建自证：打印 "x86_64 arm64"，缺哪个就报错
#   ⚠ 别用 `lipo -verify_arch x86_64 arm64 hzip`：`-verify_arch` 吃**变长架构列表**，
#     文件会被当成第三个架构名 → Xcode 26 直接报 `unknown architecture specification flag`。
#     （用法串是 `lipo <input_file> <command>`；老 Xcode 容忍那个写法，所以这句文档曾把
#      CI 的 workflow 步骤也带进同一个坑——2026-10-13 实测。）
# 打 .app bundle（Info.plist 声明 CFBundleDocumentTypes 全部支持格式）

# ① 编 FinderSync 扩展（appex 源码在 shell/hzip-findersync/；驱动会自动调这条）
./shell/hzip-findersync/build.sh --out <work>/fsx --version <ver>
cp -R <work>/fsx/hzipFinderSync.appex hzip.app/Contents/PlugIns/hzipFinderSync.appex

# ② **由内向外**签名（顺序不可颠倒：外层先签、内层后动会让外层签名作废）
codesign --force --options runtime --timestamp --sign "$ID" \
  --entitlements shell/hzip-findersync/hzipFinderSync.entitlements \
  hzip.app/Contents/PlugIns/hzipFinderSync.appex/Contents/MacOS/hzipFinderSync   # appex 内可执行
codesign --force --options runtime --timestamp --sign "$ID" \
  --entitlements shell/hzip-findersync/hzipFinderSync.entitlements \
  hzip.app/Contents/PlugIns/hzipFinderSync.appex                                 # appex 包本身
codesign --force --options runtime --timestamp --sign "$ID" hzip.app/Contents/MacOS/hzip
codesign --force --options runtime --timestamp --sign "$ID" hzip.app/Contents/MacOS/hzip-gui
codesign --force --options runtime --timestamp --sign "$ID" hzip.app          # 宿主 app 最外层
codesign --verify --deep --strict --verbose=2 hzip.app   # 自证：整条链逐层过

# ③ 公证（需 Developer ID 身份；ad-hoc 不能公证）
xcrun notarytool submit hzip.dmg --keychain-profile AC_NOTARY --wait
xcrun stapler staple hzip.dmg
```

**FinderSync appex（右键菜单）由打包驱动内嵌**：`shell/hzip-findersync/build.sh` 用 `swiftc`
产出 `hzipFinderSync.appex`，驱动 `dmg` 格式把它拷进 `Contents/PlugIns/`，再按上面 ② 的
顺序签名。要点（均为真机实证）：

- appex **必须 sandboxed**（`com.apple.security.app-sandbox`），且带 App Group
  `group.io.github.hzip.hzip`（容器是它与**非 sandboxed** 宿主之间唯一可用的通道）；
  未 sandbox 的 appex 会被 `pkd`/`pluginkit` 拒收（`plug-ins must be sandboxed`）。
- **ad-hoc 签名（`codesign --sign -`）即可注册加载**，Developer ID 非必需。所以缺签名
  身份时驱动**不会**跳过签名：内嵌了 appex 就 ad-hoc 签整包（去掉 `--options runtime`
  与 `--timestamp`，两者需真实身份）。未签名的内嵌 appex 会让
  `codesign --verify --deep` 报 `code has no resources but signature indicates they must
  be present`，整包校验失败。
- 缺 `swiftc` 或 `shell/hzip-findersync/build.sh` 时，驱动**告警并跳过** appex——`.app`
  仍产出，但右键菜单轨失效（不静默降级）。
- 宿主 `Info.plist` 的 `NSServices`（三条 `default` 文案必须与
  `crates/hzip-platform/src/context_menu/macos.rs::service_identifiers()` 逐字一致）声明
  **硬编码在模板**里：`metadata.toml` 的极简 TOML 解析器不支持数组-of-表。

产物：`hzip-<ver>-universal.dmg`（内含 `hzip.app` + `Applications` 软链 + 安装说明
README.txt；CLI 用 `ln -sf /Applications/hzip.app/Contents/MacOS/hzip /usr/local/bin/hzip` 暴露）。
`.app` 的 `CFBundleDocumentTypes` 只登记 Viewer + `LSHandlerRank=Alternate`——登记「可打开」
但不抢系统默认程序。签名身份经 `--macos-sign-id` / `HZIP_MACOS_SIGN_ID`，公证 profile 经
`--macos-notary-profile`；有身份就 Developer ID 签、没有就 ad-hoc 签（内嵌 appex 时**必做**，
见上），公证缺凭据则 dmg 不公证（并打印提示，不假装签过）。

> **「用 hzip 打开」不走命令行**：LaunchServices 把待打开文件以 Apple Event
> （`kAEOpenDocuments` → `application:openURLs:`）投给进程，argv 里**没有**它——只靠 argv
> 解析会出现「窗口起来了、压缩包没打开」（日志 `open=[]`）。GUI 经 gpui 的
> `Application::on_open_urls` 注册该事件，把 `file://` URL 转成本地路径后投进与启动意图、
> 二实例转发**同一条**意图通道（见 `crates/hzip-gui/src/app/open_event.rs`）。

> **触控栏机型关窗崩溃（上游未修，我们以 vendor 补丁兜住）**：`gpui-pre-macos` 的
> accesskit 适配器用 `accesskit_macos` 的 `SubclassingAdapter`（`object_setClass` 动态改
> 窗口内容视图的类，Drop 时再改回）——这会破坏 AppKit 触摸栏（`_NSTouchBarFinder`）
> 建在该视图上的 KVO，关闭窗口时在 display-cycle flush 里抛未捕获异常
> （`SIGILL`，仅触控栏机型）。**0.3.8 仍走同一路径**（`gpui-pre-macos-0.3.8/src/window.rs:710`
> 与 `:2365`；缺陷实现来自 `accesskit_macos 0.26.x` 的 `subclass.rs:203`/`:263`），且
> **没有任何 feature/cfg 开关**可关——安装点还在**窗口创建路径**里（`window.rs` 内
> `if !accessibility_force_disabled { … a11y_init(…) }`），不是等读屏接入才装。
> 故我们保留 `[patch.crates-io]` + `vendor/gpui-pre-macos`（当前基线 **0.3.8**）：不再改类，
> 改由普通 `accesskit_macos::Adapter` + `GPUIView` 自身实现 NSView 无障碍方法。
>
> ⚠️ **补丁失效陷阱**：`[patch.crates-io]` 只在版本**精确满足** crate 图要求时生效，否则
> cargo 仅打印 `patch … was not used in the crate graph` 并**静默回落 crates.io 原版**
> ——2026-10 就发生过：vendor 停在 0.3.6、图上却是 0.3.4，补丁从未生效，而本文当时写着
> 「已修」。**升 gpui-kit 时必须把 vendor 的版本号与其源码基线一起抬到图上要求的版本**
> （当前 `gpui-pre =0.3.8`），CI 有断言守住这一点（`.github/workflows/ci.yml` 的
> 「断言 vendor 补丁生效」：① 锁内无 `[[patch.unused]]`；② `gpui-pre-macos` 解析自
> 本地路径而非 registry；③ **补丁内容仍在**——无 `SubclassingAdapter::for_window(` 且
> 有 `accesskit_macos::Adapter::new`。抬基线时只改版本号却漏重放 hunk 会被 ③ 拦住。
> **删 patch 时本节连同该 CI 步骤一起删**）。
>
> 第二道保险（与补丁正交）：`crates/hzip-platform` 识别触控栏机型（`hw.model` ∈
> `MacBookPro1[3-6],*`），`hzip-gui` 启动时把机型写进日志；若机型带触控栏**且**显式设置
> `HZIP_MACOS_A11Y=off`，则用 `App::new_inaccessible(platform)`（进程级关闭辅助功能）
> 规避该崩溃。默认不启用——主修复是 vendor 补丁，这道开关只用于「补丁万一又没生效」
> 的现场自救。**上游合并修复后应直接升版本并删除 patch 与本段。**

### 5.5 程序图标（全平台）

**源 = 逐尺寸手工图** `crates/hzip-gui/assets/logo/hzip-<N>.png`（N ∈ 16/20/24/32/40/48/64/128/256，
正方形 RGBA）。小尺寸直接缩小大图会糊（字形变细、像素对不齐），设计者按尺寸调过的
小图清晰得多，故逐尺寸图是主源。派生产物**入库存档**（构建不需要图像工具链），
换图标后必须重跑生成脚本：

```powershell
./build/icons/make-icons.ps1        # PS 5.1 + System.Drawing，无第三方依赖
```

**每档尺寸独立解析**：① 有 `hzip-<N>.png` → 原样取用（不缩放/不加边距/不裁切）；
② 否则有 `-Source` 基准大图 → 由它缩放；③ 否则由**最近的更大档**逐尺寸图缩放
（宁缩不放；全部更小则放大并告警）。脚本逐档打印来源，便于核对。可只给部分尺寸。

| 产物 | 用途 | 生成方式 |
|---|---|---|
| `crates/hzip-gui/assets/logo/hzip.ico` | exe 图标资源（Windows） | 9 档：16/20/24/32/40/48/64/128/256；≤64 用 **DIB 条目**（资源管理器小图标/任务栏/Alt-Tab 实际取用档，兼容性最广），≥128 用 **PNG 条目**（省掉 256² 未压缩条目约 256KB）。DIB 的 AND 掩码由 alpha 推导（位=1 透明），不认 alpha 的旧渲染路径不会把透明区画成黑块 |
| `shell/hzip-shell/appx/Assets/*.png` | 右键菜单稀疏包磁贴（`AppxManifest` 的 `Square44x44Logo`(44) / `Square150x150Logo`(150) / `StoreLogo`(50)） | 同规则解析（实测 44←48、50←64、150←256 缩放） |

#### Windows：资源 ID 必须是 1

`crates/hzip-gui/hzip.rc` 与 `crates/hzip-cli/hzip.rc` 各写一条
`1 ICON "assets/logo/hzip.ico"`（CLI 侧写 `"../hzip-gui/assets/logo/hzip.ico"`），
由 `build.rs` 调 `embed-resource`
（已在依赖树内——`gpui-pre` 的 build-dependency，同版本复用；非 Windows 目标上是
no-op，交叉编译走 windres/llvm-rc）。三处取用**都**指向「exe 里 ID 最低的图标组」：

| 显示位置 | 取用方 | 无该资源时 |
|---|---|---|
| 标题栏 / 任务栏 / Alt-Tab | gpui Windows 后端注册 WNDCLASS 时的 `hIcon`（`LoadImageW(GetModuleHandleW(NULL), MAKEINTRESOURCE(1), IMAGE_ICON, …)`，gpui-pre-windows `platform.rs::load_icon`） | 空 HICON → 系统默认图标 |
| 资源管理器里的 exe 图标 | shell 取 exe 的最低 ID 图标组 | 默认图标 |
| 右键菜单项图标 | `hzip-platform::context_menu` 经典注册写 `Icon="{exe},0"`；`hzip-shell` 的 `IExplorerCommand::GetIcon` 同返 `"{exe},0"` | 菜单项无图标 |

> `.rc` 内注释刻意只用 ASCII：`rc.exe` 不带代码页参数调用，非 ASCII 会按 ANSI 解析
> （中文说明放在 `build.rs` 与本节）。

#### 其余平台

- Linux：`.desktop` 需 `Icon=<安装路径>/hzip.png`（或按图标主题名装入
  `hicolor/*/apps/`），`.deb`/`.rpm`/AppImage 各自带一份 PNG——**待 M4**。
- macOS：`.app` bundle 需 `Contents/Resources/AppIcon.icns`（`iconutil` 由
  PNG 集生成）——**待 M4**。

#### 验收锚点（本机实测）

```text
# 1) exe 资源段（PE 解析）：RT_GROUP_ICON id=1（9 条目）+ 9 个 RT_ICON，
#    重组 ICO 与 crates/hzip-gui/assets/logo/hzip.ico **逐字节一致**
# 2) 逐尺寸图未走缩放：16/32/48/64 的 DIB 条目 XOR 位图与 hzip-<N>.png
#    **逐像素一致**、AND 掩码与 alpha 一致；128/256 的 PNG 条目解码后同样逐像素一致
# 3) 按 gpui 的调用方式取图标：LoadImageW(module, 1, IMAGE_ICON, N, N)
#    → 非空，且 16/32/48 档像素与 ICO 对应档逐字节一致
# 4) shell 路径：ExtractIconExW(exe, 0) → large+small 均非空（对应 Icon="{exe},0"）
# 5) 运行时：启动 hzip-gui 后主窗口（class=Zed::Window）GCLP_HICON / GCLP_HICONSM 非空
#    对照：无 RT_GROUP_ICON id=1 的 exe（如 notepad.exe）上述调用返回 0
```

## 6. CI/CD

### 6.1 GitHub Actions 工作流

实现与职责（`git ls-files .github` 可核对）：

| 文件 | 触发 | 干什么 |
|---|---|---|
| `.github/actions/rust-build-deps/action.yml` | 被引用 | 编译依赖**单一来源**（Linux `build-essential pkg-config cmake nasm perl libfreetype-dev libfontconfig1-dev` / Windows `nasm` / macOS 镜像自带），依据见 [`build/README.md`](../../build/README.md)「编译环境依赖」A 档 |
| `.github/workflows/ci.yml` | push / PR / 手动 | `quality`（fmt、`clippy --all-targets -D warnings`、cargo-deny、`build/checks/*`、工具链↔MSRV 一致性断言）+ `test`（三平台全 workspace）+ `package-smoke`（打包相关文件一动就真打一遍包，不发布；取 `package.yml` 里 `smoke:true` 的格 = Windows x86_64 + macOS universal + Linux x86_64） |
| `.github/workflows/package.yml` | 被 release / ci 调用 | **可复用**打包作业：`plan` 算矩阵 → `package` 逐格 `cargo build --release` + `package.py` → 上传 artifact |
| `.github/workflows/release.yml` | tag `v*` / 手动演练 | `package`（全矩阵）→ `verify-msi`（真装真卸）→ `release`（汇总 + 重算 sha256sums + `softprops/action-gh-release`） |

打包矩阵（`package.yml` 里的 legs 表是唯一来源；产物命名见 §5）：

| 格 | runner | 目标 | 格式 |
|---|---|---|---|
| `windows-x86_64` | `windows-latest` | `x86_64-pc-windows-msvc` | msi, zip |
| `windows-arm64` | `windows-latest`（交叉） | `aarch64-pc-windows-msvc` | msi, zip |
| `macos-universal` | `macos-latest` | `x86_64-apple-darwin` + `aarch64-apple-darwin`（驱动 lipo） | dmg, tar.gz |
| `linux-x86_64` | `ubuntu-latest` | `x86_64-unknown-linux-gnu` | tar.gz, deb, rpm, appimage |
| `linux-arm64` | `ubuntu-24.04-arm` | `aarch64-unknown-linux-gnu` | tar.gz, deb, rpm, appimage |

关掉不需要的格（仓库变量）：`HZIP_ARM64_RUNNER=off`（不做 Linux arm64）、`HZIP_WIN_ARM=off`
（不做 Windows arm64）。矩阵由 `plan` 作业**算出来**再喂给 `strategy.matrix.include`——job 级
`if` 读不到 matrix 上下文，而可选格必须在**调度前**剔除，否则要么白排 runner、要么让可选格
把整条流水线拖红。

发版链路（`v*` tag）：

```
package（5 格矩阵）── Windows x86_64/arm64 → msi,zip
                   ├─ macOS（macos-latest）→ universal dmg,tar.gz
                   ├─ Linux x86_64（ubuntu-latest）→ tar.gz,deb,rpm,appimage
                   └─ Linux aarch64（ubuntu-24.04-arm）→ 同上
   ↓ 各格原生 runner：cargo build --release --target <triple> -p hzip-cli -p hzip-gui
   ↓ python build/package/package.py --target … --formats … --check-tag vX.Y.Z
verify-msi（windows-latest）── msiexec /i /qn → 断言文件/快捷方式/PATH/App Paths/ProgID/
                              RegisteredApplications + `hzip.exe --version` 真能跑
                              → msiexec /x /qn → 断言无残留（§8 的自动化版）
release（ubuntu-latest）── 汇总各格 artifact + 重算全量 sha256sums.txt → 建 GitHub Release
```

**与早期设计草稿的差异（每条都有实测理由，不是简化）**：

1. **不用 `dtolnay/rust-toolchain`**：工具链版本只在 `rust-toolchain.toml`（1.95.0）；workflow
   里 `sed` 读它再 `rustup toolchain install`，YAML 里不出现第二份版本号。rustup 代理认该文件，
   后续 `cargo` 自动走这条 channel。
2. **不用 `cargo nextest`**，改 `cargo test -- --test-threads=1`：hzip-gui 的用例共用一个进程，
   而 gpui-pre 的测试调度器要求「同一时刻只有测试线程在动」——并行跑时两条用例的后台线程互相踩
   （实测两次全量并行各挂 1 条、且挂的每次不同）；串行 **468/468 全过且更快**（8s vs 20s）。
   顺带省掉一个新工具依赖。
3. **两条用例被 `--skip`**（都是仓库已记录的 flake；CI 注释里逐条写明，恢复条件也在那里）：
   - `rename_and_new_folder_commands_enter_inline_edit`：**既有文档化 flake**
     （T-OPT §0/§6 项 16、T-KIT071 §7、T-BAR §7「双向偶发」）。本轮复测：隔离跑 8 次 **4 过 4 败**
     （每次都烧满 20 s 期限）——留在门禁里只会让 CI 随机变红，没有信号。修好后再删掉该 `--skip`。
   - `cancel_mid_extract_cleans_partial`：既有竞态 flake（T-STD §7.3「隔离跑 5 次 4 过 1 败」）。
   两条在本地手工单跑仍可复现——**改到相关代码时必须单跑它们**。
   （`sec_005_ratio_bomb_pipeline` / `sec_006_total_bomb_pipeline_low_quota` 原先也在这份名单里，
   原因是它们的样本在 `tests-assets/malicious/`——那目录不入库 ⇒ 干净克隆必然 panic。**2026-10-13
   起样本改为测试内自造**（`hzip-core/tests/malicious_extract.rs::build_ratio_bomb` /
   `build_total_bomb`，与样本族语义等价），两条用例在任何环境都能跑，`--skip` 已删除。）
4. **msrv 不单独起 job**：草稿里的 `1.85.0` 已过时，而 `Cargo.toml` 的 `rust-version`（1.95）与
   钉住的工具链本就是同一版本线——单独起 job 只会装同一条工具链。改为 `quality` 里一条断言：
   两边不是同一版本线就红。
5. **`verify-msi` 断言按 `.wxs` 逐条落地**：安装目录文件（含可选壳扩展两件）、开始菜单/桌面
   快捷方式、机器 PATH、`App Paths`、ProgID `hzip.Archive`、`RegisteredApplications` +
   `Capabilities`，并跑一次 `hzip.exe --version`；卸载后断言文件/快捷方式/注册表/PATH 无残留。
   WiX 的 `.wixpdb`（调试符号库）留在 artifact 供排查，但**不作为 Release 资产**发出。
6. **`nightly.yml` 未落地**：它依赖 `fuzz/**` 与 `benches/**`（05 T51），两个目录当前都不存在，
   现在铺一条只会是空跑。落地时按原设计补全矩阵 + 覆盖率 + fuzz 批次。
7. **Gitee 镜像 job 未落地**：上一版文档那句「见 release.yml 末尾注释」是**设计描述**——
   迁 GitHub 前的工作区里根本没有 `.github/`。主仓在 GitHub；若要做 Gitee 镜像，另开一条
   workflow（`git push --mirror`），不在本版范围。

8. **打包工具由 CI 自己装、`ldd` 进日志**：`package.yml` 的「打包工具」步骤按平台装
   WiX（版本读 `metadata.toml` 的 `wix_version`，不在 YAML 里再写一遍）、Linux 的
   `dpkg-dev rpm squashfs-tools desktop-file-utils appstream`；macOS 用镜像自带的
   `hdiutil/iconutil/sips`。runner 镜像**不带**这些，不装就是「工具缺失」硬错误（driver 不猜不降级）。
   另外 Linux 腿把 `ldd` 打进日志：`metadata.toml` 的 `[deb]/[rpm]` 是**手写**依赖清单，换依赖树
   后最容易忘，2026-10-12 正是靠它发现 `libfontconfig1` 漏了（详见 T-PKG §7.2）。

9. **GUI 界面用例只在 debug 档可跑**（release 档编译期就拒绝）：锚点用例靠 gpui-pre 的
   `debug_bounds` 取边界，而 `debug_selector` 在 release 下是**有意的 no-op**（上游注释：换取每帧
   零开销）⇒ `cargo test --release -p hzip-gui` 实测 55 条整片报「锚点缺失」。与其让人对着假红灯
   找根因，`crates/hzip-gui/src/lib.rs` 用 `#[cfg(all(test, not(debug_assertions)))] compile_error!`
   在编译期把话说清。故 CI 与本仓库的测试门禁一律走 debug（本文件第 6 条那套命令），release 档
   行为验证只有「打包 + 手工检查单」（03 §2.7）这一条路；release 档要跑非界面用例用
   `cargo test --release -p <crate>`。

**签名**：不提供凭据时 Windows 产 unsigned MSI/zip、macOS 产 unsigned `.app`/dmg，两处都在日志里
显式告警（04 §9 允许，但必须显著声明）。要签名就把证书放进 Secrets，并在 `package.yml` 的打包
步骤上传 `--sign-pfx/--sign-password`（Windows）或 `--macos-sign-id/--macos-notary-profile`（macOS）
——**本版未接 Secrets 管道**（避免在没有证书的仓库里挂一段永远不生效的配置）。

### 6.2 缓存与预算

- `Swatinem/rust-cache@v2`：`test` 作业按 runner OS 分 key；打包作业按**矩阵格**分 key（`matrix.label`）
  ——每格是独立的 `--target` 产物，共用 key 只会互相驱逐；
- 打包各格并行、`fail-fast: false`（一格失败不取消其余，便于一眼看出是哪一格挂的）；artifact 保留 14 天；
  Release 资产 = 各格产物 + 全量 `sha256sums.txt`（WiX 的 `.wixpdb` 除外）；
- 本地预算参照（2026-10-12 本机 Windows 实测，依赖已缓存）：`cargo test --workspace` 串行 **≈50 s**
  （并行反而 4 min，见 6.1 差异第 2 条）；`cargo clippy --workspace --all-targets` **≈45 s**；
  Windows 一格打包（release 二进制已就绪）**≈10 s**。CI 上绝对时间取决于 runner 与缓存命中率；
- nightly 全矩阵（覆盖率上传 + fuzz 批次，原目标 < 40 min）**未落地**：依赖 `fuzz/**`、`benches/**`（05 T51）。

## 7. 发布流程（版本发布检查单）

1. **版本准备**：更新根 `Cargo.toml` workspace 版本号（`cargo workspaces version` 或手动，全部 crate 同版本同步发布）；
2. **准出确认**：核对测试准出标准（[03-测试方案及用例.md](03-测试方案及用例.md) §1.5 与平台阶段准出 §1.3）：P0 用例 100%、覆盖率门禁、性能无回归、对应平台阶段检查单签字归档；
3. **变更日志**：`git-cliff -o CHANGELOG.md` 生成并人工修订（安全类修复显式标注）；
4. **打 tag**：`git tag -s vX.Y.Z`（签名 tag），push 触发 release 工作流；想先演练一次就用
   **Actions → release → Run workflow**（填已存在的 tag + `dry_run=true`）：全矩阵照跑、`verify-msi` 照验，
   只是不建 Release；
5. **产物验证**：CI 已自动跑 Windows MSI 的安装/卸载校验（release.yml 的 `verify-msi`）；
   人工再按 §8 清单逐平台抽验（MSI/dmg/deb/rpm/AppImage/portable zip 各一份）；
6. **公示**：Release Notes 附 sha256、THIRD-PARTY-NOTICES、已知问题清单；
7. **回滚预案**：GitHub/Gitee Release 标记 pre-release/撤回；MSI/商店分发走版本下架流程。

版本策略：v0.x 期间 minor 递增；v1.0 起遵循语义化版本，公开 API 冻结范围（02 文档 §11）即稳定性承诺边界。

## 9. 许可与合规

**hzip 自身以 `GPL-3.0-or-later` 发布**（用户决策 2026-10-12；GNU GPL v3 全文见仓库根
`LICENSE`，取自 <https://www.gnu.org/licenses/gpl-3.0.txt>，逐字未改，sha256
`3972dc9744f6499f0f9b2dbf76696f2ae7ad8af9b23dde66d6af86c9dfb36986`）。本节取代旧口径
「拟 MIT OR Apache-2.0」。

### 9.1 唯一事实源：正文 + 两处 SPDX 必须一致

| 位置 | 内容 | 作用 |
|---|---|---|
| `LICENSE`（仓库根） | GPL-3.0 正文 | **法律文本本体与唯一事实源**；打包驱动据此把全文装进各产物 |
| 根 `Cargo.toml` `[workspace.package] license = "GPL-3.0-or-later"` | SPDX 表达式 | 18 个 crate 经 `license.workspace = true` 继承；`cargo metadata` 与发布元数据的来源 |
| `build/package/metadata.toml` `spdx = "GPL-3.0-or-later"` | SPDX 表达式 | deb `copyright`、rpm spec、AppStream、dmg 说明的许可元数据来源 |

SPDX 表达式是正文的**机器可读缩写**，以 `LICENSE` 为准。三者任一漂移都会造成「产物声称的
许可 ≠ 随包全文」的合规缺陷，故由构建期硬门禁兜住（9.4）。

### 9.2 依赖许可策略：从「禁止 GPL 进入链接边界」改为「允许与 GPLv3 兼容者」

**旧策略**（本项目原计划 MIT OR Apache-2.0）：`deny.toml` 拒绝一切 GPL 类传染协议进入
链接边界——因为宽松许可代码一旦与 GPL 代码链接，整包会被抬升为 GPL，与「以宽松许可
发布」的意图直接冲突。

**现策略**：本项目自身即 `GPL-3.0-or-later`，其传染强度 ≥ 任何 GPLv3 兼容协议 ⇒ 上述
冲突不再存在，故口径改为**按兼容性放行**：

| 处理 | 协议 | 理由 |
|---|---|---|
| **允许** | `GPL-3.0(-only/-or-later)`、`LGPL-3.0(-only/-or-later)` | 与本项目同族 / 弱传染，可合法链接进 GPLv3 产物 |
| **允许** | `GPL-2.0-or-later` | `-or-later` 可升版到 GPLv3，可与 GPLv3 组合（FSF 兼容性矩阵） |
| **拒绝** | `GPL-2.0(-only)`、`LGPL-2.0/2.1(-only)` | 与 GPLv3 **不兼容**（GPLv2-only 无法升到 GPLv3；GPLv3 §7 额外限制与 §11 专利条款与 v2-only 冲突），链接即违法 |
| **拒绝** | `AGPL-*` | 与 GPLv3 不兼容且传染更强（网络交互即触发分发义务），会把本项目整体抬为 AGPL，超出既定意图 |
| **拒绝** | `SSPL` | 非 OSI 认可、与 GPLv3 不兼容 |

白名单制与例外机制不变：只放行 `deny.toml` `[licenses].allow` 显式列出的协议，未列出者
一律判红（新增依赖须评审后显式加入）。

> **cargo-deny ≥ 0.18.4 的配置口径（2026-10-13 实测迁移）**：`[licenses]` 的
> `version`/`default`/`deny`/`copyleft`/`allow-osi-fsf-free`/`unlicensed` 键已被**删除**，
> 写上就是 deprecated 硬错误；「默认拒绝」改成内建语义，所以**上表里那些「拒绝」靠不写进
> `allow` 表达**（原先的显式 `deny` 列表已无对应键，已删）。`allow` 的条目只能是**单个**
> SPDX id（可带 `WITH` 例外）——`"MIT OR Apache-2.0"` 这种表达式会让解析器报
> `expected a WITH here`。另：`copy-files` 是 `cargo about` 的键，cargo-deny 不认（写上
> 直接解析失败）——本仓库那份曾同时踩中这三处，CI 的 `cargo deny` 因此**从未真正跑通过**。
>
> **unrar 的正确记法**：`unrar` / `unrar_sys` 这两个 crate 的清单声明是 `MIT OR Apache-2.0`，
> cargo-deny 只能看到清单 ⇒ 原先那两条 `[[licenses.exceptions]] allow = ["UnRAR"]` 永不匹配
> （每次报 `license-exception-not-encountered`），已删。真正的义务是**内嵌的 unrar C 源码**
> 的 UnRAR 许可（允许解压用途免费分发、禁止拿它重实现 RAR 创建）——hzip 仅解压（D2）满足，
> 该义务登记在 `deny.toml` 注释与本文件，不靠一条永不生效的配置装作合规。

**安全公告（advisories）口径**：`unmaintained = "workspace"`（只对**直接依赖**报无人维护；
上游链条里的 5 条——instant/paste/rustybuzz/ttf-parser/unsafe-libyaml——我们无权修，卡门禁
只产生噪音），并逐条登记 4 个 `ignore`（每条都带 `reason`，见 `deny.toml`）：
`RUSTSEC-2026-0245/-0246`（sevenz-rust：路径穿越在我们的调用链之外——7z 解压走
`BlockDecoder::for_each_entries` 拿流式 Read 再自净化落盘，从不调用 `de_funcs::decompress_impl`；
且 0.6 已停更）、`RUSTSEC-2026-0194/-0195`（quick-xml：被 `zbus_xml` 固定 ^0.38，只解析本机
D-Bus 的 XML，非用户输入）。**可修的都已修**：`time` 0.3.45 → 0.3.55（RUSTSEC-2026-0009 栈耗尽）。
想按最严口径自查：把 `unmaintained` 临时改成 `"all"` 再跑 `cargo deny check advisories`。

> 兼容性依据：FSF「Various Licenses and Comments about Them」的 GPL 兼容性矩阵；GPLv3
> §7（额外限制）、§11（专利许可）与 GPLv2-only 的冲突是 `GPL-2.0-only` 被拒的根因。

### 9.3 分发义务（GPLv3 条款 → 本仓库的落实动作）

| 义务 | 条款 | 落实 |
|---|---|---|
| 随目标代码分发许可全文 | §4/§6 | 打包驱动**自动**把根 `LICENSE` 装进各产物：deb/rpm/AppImage 的 `usr/share/doc/hzip/`、zip/tar.gz 与 portable 根目录、macOS `.app/Contents/Resources/`、**MSI 安装目录 `INSTALLFOLDER`**（驱动生成 `licenses.wxi`，`HasLicenses` 条件引用）。安装向导里的许可条款页（WiX `--license-rtf`）是与「全文落盘」独立的**可选项**，默认关（见 T-LIC 遗留项） |
| 提供对应源码 | §6 | 源码仓库公开：`repository` / `homepage` / `issues_url` = <https://github.com/flyl3una/hzip>（发布 tag 与产物一一对应） |
| 修改版本显著声明 | §5 | 发行版由本仓库 tag 直接构建，未附加修改 |
| 不得附加额外限制 | §7 | 不添加与 GPLv3 冲突的 EULA/使用条款；第三方组件（如 unrar）的下游义务在其自身许可中声明，不与 GPLv3 冲突 |
| 下游自动获得授权 | §10 | 随全文声明即生效，无需额外动作 |
| 版本与构建信息可见 | §6 | GUI「关于 hzip」显示版本号；许可证行在**编译期**由根 `LICENSE` 派生（9.4），使产品 UI 与随包全文同源 |

**unrar C 库**：许可允许解压用途免费分发，禁止用于创建 RAR 档案的再实现——hzip 仅解压
（D2）满足约束；该许可**不是** GPL 类传染协议，可与 GPLv3 产物共存（`deny.toml` 显式
例外）；发行版合规构建仍提供 `--no-default-features` 剔除路径（§3.2）。

### 9.4 「关于 hzip」许可证行的编译期派生与防漂移

许可证展示**不得**是手写字符串——它会与正文各自漂移，且「显示一种、附另一种」是最严重
的合规错误。机制：

1. `crates/hzip-gui/build.rs::derive_license()` 读取仓库根 `LICENSE`，由**正文**派生许可身份，
   写成 `$OUT_DIR/license.rs` 供 `about.rs` `include!`：常量 `SPDX`、`NAME`、`VERSION`、
   `DATED`、`DISPLAY`（`DISPLAY` 由 `NAME` + `v{version}` 拼出 ⇒ `GNU General Public
   License v3`）。同时把根 `LICENSE` 声明为 `cargo:rerun-if-changed` 依赖——改正文必重编译，
   杜绝旧文案静默上线（与 `locales/` 同款守卫）；
2. 「关于 hzip」弹窗的许可证行由 **i18n 模板 + 派生常量**渲染：`about.license` 词条
   （`locales/chrome.toml`，zh-CN/en 双语）只留框架文案，`{spdx}` / `{name}` 占位符由
   `crate::tr_with` 填入派生常量（语法同 `status.selected`），不再写死 `MIT OR Apache-2.0`；
3. **清单与正文不一致则构建失败**：`derive_license` 断言 `LICENSE` 首行 = `GNU GENERAL
   PUBLIC LICENSE`、次行 = `Version 3, 29 June 2007`，并**交叉校验** `CARGO_PKG_LICENSE`
   （即 `Cargo.toml` 的 `license`）主体必须为 `GPL-3.0`（剥离 `-only`/`-or-later` 后）——
   任一方变化导致不匹配即 `panic!`，编译期硬门禁，人工无需核对。

> 注：交叉校验覆盖 `LICENSE` ↔ `Cargo.toml`；`build/package/metadata.toml` 的 `spdx` 不参与
> 编译期校验（非本 crate 可见），其一致性由打包驱动与 9.1 的评审约定保证。

三者（产品 UI / 随包 `LICENSE` / crate SPDX）由此被构建强制绑定为同一事实。
