# UI 线程阻塞审计与后台化方案

> 立此文档的触发（用户口径 2026-09-24）：**在 hzip-gui 里展开压缩包内的 cpio 目录后，
> 主界面卡住无响应一段时间**。用户要求：把「哪些操作会阻塞 UI 线程」完整整理出来，
> 并给出调整方案；调整原则是——
>
> 1. 所有可能 > 0.5 s 的耗时操作都要**弹窗显示进度**并在**后台任务**里做；
> 2. 用**原子闸**避免同一操作被连点/多入口重复触发；
> 3. 所有用户操作都要让用户**有明确感知**（在做什么、到哪了）；
> 4. 所有任务都要在**任务中心**留痕，**失败要记失败原因**。
>
> 本文是「现状审计 + 方案」，代码落地随各条目推进（已修条目在 §3 标注）。

## 1 判定基准

- **UI 线程** = gpui 的事件/渲染线程：`Render::render`、泵每 tick 的批处理
  （`ui/shell/runtime.rs` 的 `cx.spawn(async { loop { … } })` 同步前缀）、
  `AppShell` 的事件回调 / `on_action` 闭包 / `dispatch_toolbar` 各分支、
  `prompt_on_event`/`on_event` 这些对话框回调。
- **算「已后台化」**：`std::thread::spawn`（或 `run_open_flow` 的 `hzip-open` 专用线程）、
  `cx.background_executor().spawn(smol::unblock(...))`。只有这些才不算阻塞点。
- **共享状态**：`AppData`（`Arc<Mutex<AppData>>`）是唯一数据面。UI 线程**每帧**都要
  取它（渲染菜单上下文等），所以：
  - 后台线程**持锁**做重活 ⇒ 主界面停帧（§2-B1/B3/B6）；
  - UI 线程**持锁**做 O(n) 活 ⇒ 后台任务与自己的下一帧都被堵（§2-B5/B8/B9）。
- **规模相关性**是分档依据：与条目数/字节量成正比的路径优先修。

## 3 本轮已落地

### 3-1 `caps_edit` 记忆化 + 快照投影（消 B13）
`AppData::caps_edit()` 现在按**档案路径**缓存（`caps_edit_cache`）；`export_snapshot`
把它与 MRU 一起投影进 `AppStateUiSnapshot`，渲染侧只读 `ShellState`。
⇒ `render` 不再每帧开文件嗅探、不再每帧锁 AppData。

### 3-2 预览 / 外部打开 / 复制：**锁外三段式**（消 B4，缓解预览类）
统一成「锁内 `take_browser()` → 锁外读/物化（可跨线程）→ 锁内 `restore_browser()`」：
- `open_selection_entry` 预览分支：`MainViewModel::preview_in(&Browser, …)` 在后台执行器上跑；
- 外部打开物化：`materialize_in(&Browser, …)` 在专用线程上跑，完成后**任务中心留痕**
  （成功/失败都记，失败带 HZ 码原因）；
- `copy_selection`：从「UI 线程 + 持锁」改为**后台线程 + 进度窗**（见 §3-6），
  完成后经信号写系统剪贴板。

### 3-3 浏览密码门：重开离 UI 线程（消 B1）
新 `shell::begin_browse_gate_reopen`：`PasswordSubmit` 事件在 shell 层截住 →
专用线程锁外 `engine.browse`（带密码）→ 锁内装会话 + 门状态收口 → 信号回投
`EntriesChanged` + 任务中心 `record_op("open", …)`。密码窗在门解除前保持可见
（投影不变 ⇒ 不关窗）。`prompt.rs` 门分支只保留取消。

### 3-4 压缩提交后台化（消 B2）
`LaunchIntent::Compress` 的 `submit_compress_locked` 改走
`background_executor().spawn(smol::unblock(…)).await`（与解压分支同口径）。

### 3-5 配置读取缓存（消 B6 的读、B12、B16、B17、B18 的读）
`hzip-config::Config::load()` 加**进程内缓存**：每次调用只 `metadata()`
（stat，微秒级）比对 mtime + 长度，命中直接克隆返回；`save()` 落盘后显式失效。
⇒ GUI 里四十来处 `Config::load()`（含渲染/每次操作路径）不再各自读盘 + TOML 解析。
别的进程改写配置照样立刻可见（stat 守卫）。

### 3-6 「操作进度窗」通用化 + 任务中心通用记录
- `open_progress` 的窗口形态泛化为 **`OpLabels{title_key, running_key, done_key, record_kind}`**：
  打开、复制… 共用同一窗体与重绘节拍，动词随操作变（新增 `openprogress.title_copy` 等 5 个 key）。
- `JobsViewModel::record_op(kind, name, path, result)`：非任务操作（打开/复制/外部打开）
  统一走任务中心留痕，失败带明确原因（`job_kind_label` 新增 `copy`）。
- `copy_selection` 现在：`session_switch` 闸（连点只触发一次）+ 后台线程 + 进度窗
  （明细行「正在解出选中条目…」）+ 任务中心记录 + 失败不自动关窗。

### 3-8 `Reveal`（在文件管理器显示）挪后台
`reveal_in_file_manager` 走 ShellExecuteW / 资源管理器 IPC，系统响应不可控（慢盘/
网络路径百毫秒级）。改为 `std::thread::spawn` 内调用，失败只留 warn。

### 3-9 分栏宽度写盘去抖
`on_resize` 的内存值照旧逐 tick 同步（重新显示插回用它），落盘改为**延迟任务 + 代数
守卫**：400 ms 内没有更新的 tick 才写——拖动中零写盘，松手后的最终宽度不丢。

### 3-10 复核修正（第二轮审计）
- `handler.caps()` 各 fmt crate 全是**静态常量**返回（不打开文件）——真正做文件 IO 的
  只有 `registry.sniff()`（`sniffer.rs` 开文件读 512 B；组合档 `sniff_composite_replay`
  逐层重建解码链，深度上限 3）。故 §3-1 的记忆化只对 `caps_edit`（走 sniff）有意义。
- `views/progress/mod.rs::dispatch_rows` 每次泵 wake 的 `Config::load()`：**已由 §3-5
  的缓存消除**（不再读盘/解析）。
- `op_window` 参数窗「开始」的提交（`submit_extract` ×N / `submit_compress`）在配置缓存
  之后降级为**轻微**（每档案 ≈0.1 ms：仅 2 把锁 + 入队 + 线程启动），暂不改结构。
- 泵批内 `export_snapshot`/`refresh_browse_rows` 仍在 AppData 锁内（§B5/B3 待办）——
  即「快照导出的代价从渲染帧转移到了泵 wake」，仍需 P0 收口。

### 3-7 UI 线程滞后看门狗（测量面）
`app::ui_lag::UiLag` —— RAII 计时守卫，超 150 ms 记 warn、超 500 ms 记 error
（带块名与耗时，落 `hzip-YYYY-MM-DD.log`）。已挂在**主窗口渲染**与**泵批处理**两处：
再现卡顿时日志直接点名是哪一帧的哪段同步活，不用再靠猜。

### 3-11 会话保活重开 + 行重建改「只请求」（消 B3/B5/B9）

泵批内不再自己干活，只两件便宜事：

- `AppData::browse_session_reopen_request()`：`is_open` + `exists` 判断，需要重开就
  **返回路径并置在飞标志**；真活交 `shell::spawn_browse_reopen`（专用线程：锁内取
  引擎 → 锁外 `browse` → 锁内 `finish_browse_reopen` 装会话 + 重建行；成败都清标志，
  失败清空行集、下次仍可再试）。
- `shell::spawn_rows_rebuild`：`rows_rebuild_in_flight` 去重（多窗口 + 多信号同 tick
  只跑一次），后台线程在锁内重建 O(行集) 派生，完成后投新信号
  `VmSignal::BrowseRowsRebuilt`（明确**排除**在重建触发条件之外，避免自激回路）→
  下一泵批重导快照。

`toggle_tree_expand` 因此只改展开集（O(1) 数据面），行重建由调用方发信号触发。
`ensure_browse_session` / `refresh_browse_rows` 两个旧入口随之删除（唯一调用点已在
泵内改写），避免「还有一条同步重开的路」。

### 3-12 配置写盘异步化（消 B6 写侧、B15 写侧）

`hzip-config` 新增 `Config::save_async`（**最新覆盖** + 后台合并写线程：配置是整体
快照，丢中间态无副作用，故不需要队列）+ `Config::flush_pending_saves`（退出前收口，
上限 2 s）。GUI 的唯一写盘尾步 `persist` 与分栏宽度写都改走它；`graceful_shutdown`
开头 flush。写线程清标志后会**复检**待写槽，接住「清标志瞬间来了新请求」的竞态。

### 3-13 关联/右键菜单状态缓存（消 B7/B10）

`ui::contracts` 新增 TTL(60 s) 缓存（键含扩展名集，顺序无关）+ `warm_assoc_status_cache`
（后台线程预热）+ `invalidate_assoc_status_cache`（应用/清除后失效）。启动期预热一次，
设置页装配与 `reload`（每次设置生效/切语言都会跑）常态命中缓存 ⇒ 零注册表/子进程查询。

### 3-14 B8 复核：不改

`begin_delete_files` 的锁内活是 `effective_selection_ids`（隐式目录子树展开）+ 变更集
构造，两者都是**一次性 O(选中)** 纯内存操作（10k 选中 ≈ 数十 µs~ms），且删除前还要用户
确认——不属「卡住」级，故本轮不动（写在这里以免以后重复排查）。

### 3-15 B11：保留（附理由）

系统通知走 gpui 的 `cx.show_system_notification`（UI 线程 API，Windows 上底层是 COM），
且只在「无主窗口」的兜底路径触发（有主窗口时是界面内 toast）。脱离 UI 线程需要绕开 gpui
直接调平台 API，收益小于维护成本，故保留并登记。

### 3-16 剪贴板可用性进快照（消 B14）

`has_clipboard` 由每帧查询改为快照字段（泵按批导出，一次一批），`render` 只读 `ShellState`。

### 3-17 预览载荷 Arc 化 + 后台派生（消 B16/B17）

- `PreviewPayload.text/hex_lines` → `Arc<Vec<String>>`（重绘只克隆引用，不再整表克隆）；
- 图片在**载荷构造时**就解码 + BGRA swap + 封成 `Arc<RenderImage>`（渲染帧零拷贝零解码）；
- `payload_from_preview` 随 `preview_in` 一起在**后台执行器**上跑（HEX 逐行格式化与
  图片解码都不再落 UI 线程）。

### 3-18 变更集判定改闭包（消 B18）

`append_changeset(files, is_existing: impl Fn(&str) -> bool)`：调用方直接借用 VM 内部
条目名判存，不再先把整表名字克隆成 `Vec<String>`（大档案下每次添加/粘贴都白抄一遍）。

### 3-19 任务行集 Arc 化 + 派生行缓存（消 B19 与审计 ⑦）

- `JobsViewModel.rows` → `Arc<Vec<JobRow>>`（写时复制；8 处变更点走 `Arc::make_mut`）：
  `export_snapshot` 只克隆引用（不再深拷贝全部行/失败明细）；
- 任务中心视图按**源行集 `Arc` 身份**缓存派生行（`Vector<JobsRowUi>`），未变则复用
  （旧实现每帧全量重建 i18n/格式化）。

### 3-20 菜单「刷新」接线（消 B20）

`ToolbarAction::Refresh` 原先落到 `handlers.on_toolbar` 兜底（默认 no-op，点了没反应）。
现在真重读：走 `open_flow`（后台线程 + 操作进度窗 + 任务中心 `kind = refresh`），
并在失败时把原会话浏览器放回（刷新失败不该让会话空掉）。

### 3-21 换会话**代数**：新增操作顶替旧操作（消 B23）

用户实测（2026-09-24）：「我打开了 cpio.gz，没有展开里面的 cpio，这个时候我再打开了一个
qcow2.gz 文件，但是出现了一个进度弹窗还是在打开这个 cpio 文件。我重新打开新压缩包后，
不应该被老压缩包内容干扰。」

根因有三层：

1. **旧流程可能后落地**：两次「换会话」各自在后台线程跑，没有任何次序约束——旧的
   `install_browser` 晚于新的执行，就把用户刚打开的档案盖回旧档案（还带着自己的进度窗）；
2. **旧进度窗没人关**：窗口按展示名去重、且失败不自动关——旧档案的窗会一直留在屏幕上，
   用户看到的就是「还在打开那个 cpio」；
3. **旧档案的会话残留**：顶层打开新档案时没有清嵌套会话栈，旧档案的内层层级/临时文件
   继续挂在新会话上。

修法（`AppData::begin_session_switch` / `session_switch_is_current` / `end_session_switch`）：

- 每次**有目标**的换会话（打开档案 / 进入容器 / 展开延迟层 / 刷新）发起时代数 +1，并把
  `(键, 展示名)` 记为在飞目标；
- **同目标**连点 → `Duplicate`（去重，不重复起线程，替代原先的「原子闸 + 静默丢弃」——
  那套会让「打开 A 后立刻打开 B」被整条丢掉）；
- **不同目标** → 顶替：调用方**立刻按旧展示名关掉旧进度窗**（`open_progress::close_by_label`），
  旧流程在落账前比对代数发现已过期 → 返回哨兵 `SESSION_SUPERSEDED`，`run_open_flow` 认它 =
  **静默收尾**（关自己的窗、不写任务中心、不报错、不发信号）；
- 顶层打开新档案额外调 `reset_nested_sessions()`：清空嵌套栈并尽力删除各层临时文件；
- 保活重开（编辑后）也加了「会话已被别的操作恢复就丢弃结果」的护栏。

原子闸 [`AppState::session_switch`](crate::app::state::AppData::session_switch) 只留给**无目标**
的重活（复制物化 / 弹出层）——它们不受顶替影响。

已知取舍：被顶替的旧 `browse` 无法中断（core 没有取消令牌），会白跑完但结果被丢弃。

## 4 方案（对未修条目的调整原则）

**统一范式**（`run_open_flow` + `open_container` 为样板）：

1. **重活三段式**：锁内只取句柄/参数（微秒）→ 锁外（必要时专用线程）做重活 →
   锁内一次性落账。**任何**后台路径都不得在持 AppData 锁时做 I/O 或 O(n) 计算。
2. **原子闸**：会话/浏览器级别的重活统一走 `AppData::session_switch`
   （`SessionSwitchGate` + RAII 闸票，互斥不排队）；任务级别的重活按
   （种类, 目标）去重（如 TestIntegrity 同档案只允许一条）。
3. **进度可见**：> 0.5 s 的操作一律走「操作进度窗」（`OpLabels` 参数化 + `OpenDetail`
   阶段/字节明细），窗口在**超过门槛**后才弹（小操作不闪窗），失败**不自动关**。
4. **任务中心留痕**：所有操作写一行（`record_op`/`record_open`），失败写明确原因
   （HZ 码 + 人读文案）。
5. **UI 线程只做派生**：行集/快照的 O(n) 构建搬到后台，产出 `Arc<Vec<_>>` 后原子替换
   （`nav_rows`/`dir_rows` 已是 Arc；`JobRow` 待 Arc 化）。

## 5 验收方式

- 看门狗日志：`hzip-YYYY-MM-DD.log` 中不得出现 `UI 线程卡顿`（error 级）；
  warn 级长帧应只出现在「大档案首次索引」这类一次性场景。
- 交互验收：打开含大内层容器的组合档 → 双击展开 → 全程可交互（转圈不停、能切页签）、
  明细行数字持续更新、连点只触发一次、失败不自动关窗且任务中心有原因。
- 回归：`cargo test --workspace`、`cargo clippy --workspace --all-targets`、
  `python build/checks/deps-direction.py`。
